# 남은 일

## 지금 할 것

**2026-08-05 현재 — 언니가 열흘째 실제로 쓰고 있다.** 예약 13건 이상, 손님 이름을 꼬박꼬박 넣고 있고, 설정에서 시술(매직셋팅·남자펌)을 직접 추가·삭제했다. 두 번째 피드백 세 건(시술 순서, '마지막', 금액)을 고쳐 **v17로 배포한 상태.**

- [ ] **언니 폰에서 갱신 확인** — 앱 완전히 닫기 → 열고 10초 대기 → 닫기 → 다시 열기 → 설정 시술 목록에 **`↑` 버튼**이 보이면 성공
  - 안 보이면 **어느 브라우저로 홈 화면에 추가했는지**(크롬/삼성 인터넷)부터 확인한다. 브라우저가 다르면 데이터도 따로다
  - 앱을 지우거나 새로 깔 필요 없다. 지우면 예약이 같이 사라진다
- [ ] 그 전에 언니에게 **설정 → 파일로 내려받기** 한 번 시켜두기 (보험). 열흘치가 쌓여 있어 이제 진짜로 잃을 게 있다
- [ ] **금액을 실제로 넣는지** 관찰 — 선택 입력이라 안 넣어도 앱은 돈다. 안 넣으면 손님 이력의 금액 칸은 영원히 빈다
- [ ] 언니에게 주고 **한 달** 관찰 → **손님 이름을 눌러보는가**
- [ ] 언니에게 물어볼 것
  - 종이에 시술을 뭐라고 적는지 (파마/펌, 컷트/커트 …)
  - **"컷트"라고만 쓰면 남녀 구분을 어떻게 하는지**
  - **예약 시간을 바꿀 때 주로 어떻게 바뀌는지** — 하루이틀 미루기가 대부분인지, 시각이 크게 바뀌는지
  - **손님이 안 왔을 때 어떻게 하는지** ← 새로 생긴 질문. 아래 참고
  - **이름 대신 `3364`·`젬마컷`·`신규남펌` 이라고 적은 건 무슨 뜻인지** — 이름을 모르는 손님을 나름대로 표시한 것으로 보인다. 규칙이 있다면 앱이 도울 여지가 있다

세 번째 질문의 답에 따라 `내일로 미루기` 버튼이 나을지 드래그가 나을지 갈린다.

### 아직 안 풀린 것 — 노쇼

`총 N회 방문` 에서 **다가올 예약은 빠지지만, 예약해놓고 안 온 손님은 날짜가 지나면 자동으로 방문이 된다.** 언니가 `취소로 표시` 를 눌러야만 빠지는데, 안 온 손님을 매번 취소 처리할 것 같지 않다.

숫자를 더 정확해 *보이게* 만들었지만 이 구멍은 그대로다. **언니가 실제로 어떻게 하는지 듣기 전에는 고치지 않는다** — 하루 지난 예약에 "오셨나요?" 를 묻는 화면은 안 하던 일을 하나 늘리는 것이고, 그게 이 앱이 가장 조심하는 것이다.

### 안 하기로 한 것

**영업시간 밖 시각에 되묻기.** 오후 예약을 넣을 때 '오후'를 깜박하면 오전 2시로 저장되는 길이 남아 있다. 확인 팝업을 넣을까 했지만 **"오전 2시에 머리하는 사람은 없어서" 목록에서 바로 눈에 띈다**는 판단으로 뺐다. 하루 5~10건 넣는 화면에 팝업을 하나 더 두는 값이 더 크다.

## 갈림길 — 2단계를 할 것인가

| 언니 반응 | 다음 |
|---|---|
| 잘 쓴다 + 손 입력도 괜찮다 | 사진 판독 **불필요** |
| 잘 쓴다 + 손 입력이 귀찮다 | 사진 판독 **투입** |
| 안 쓴다 | 판독을 붙여도 소용없음. 원점 재검토 |

가운데가 가장 가능성 높다. 관찰 단계에서 이런 말이 나왔다.

> "달력에 쓰고 바로 폰에 기록은 같은 일을 2번 하는 거잖아. 안 할 것 같아"

그 예측이 맞으면 손 입력만으로는 오래 못 간다. 그때 사진 판독이 **"있으면 좋은 것"이 아니라 "없으면 앱이 죽는 것"** 이 된다.

## 2단계 — 사진 판독 (조건부)

### 판독 테스트 결과 (샘플 달력)

예약 6건 **전부 찾아냄. 놓친 것 0건.** 날짜 6/6 정확 (칸 밖으로 뺀 사선 표시도 제 날짜에 붙임).

| | |
|---|---|
| 날짜 | ✅ 6/6 |
| 시각 | ⚠️ 1건 애매 (`10:20` vs `10:30` — 사람이 봐도 헷갈린다) |
| 시술 | ⚠️ **종이 어휘와 앱 목록이 다르다** — 파마↔펌, 컷트↔남자커트/여자커트 |
| 이름 | ⚠️ 전례 있음 — "화선언니"를 "화선이나"로 오독 |

**시술명은 목록으로 교정할 수 있지만, 이름은 대조할 목록이 없어서 틀리면 그냥 틀린다.**

> 시술 어휘 문제는 이미 손을 썼다 — 언니가 시술을 직접 추가·삭제할 수 있고, `펌 ← 파마` 별칭도 들어갔다.

### 만들 것

1. 설정에 **AI 열쇠 칸** — 넣으면 켜지고 비우면 꺼진다
2. **카메라 버튼** — 열쇠가 있을 때만 나타난다
3. **확인 화면** — AI가 자신 없어 하는 항목만 **노란색.** 언니는 노란 것만 보면 된다
4. **덮어쓰기 규칙** — 사진은 `source: 'photo'` 인 것만 갈아엎고, 손으로 넣은 건 안 건드린다

**기존 코드는 거의 안 건드린다.** 처음부터 "판독은 부가 기능이고 없어도 앱은 온전히 돈다"는 원칙으로 만들어서, 버튼 하나와 화면 하나를 얹는 일이 된다.

### 비용

사진 1장당 약 20원. 하루 1장이면 **월 600원** 정도.

**열쇠를 누가 넣느냐**에 따라 누가 내는지 정해진다. 아무도 안 넣으면 판독만 꺼지고 앱은 그대로 돈다.

## 몇 년 뒤 — 직원과 공유

샵이 확장되면 나올 얘기. **지금 구조로는 불가능하다** — 데이터가 각자 폰 안에만 있어 두 사람이 쓰면 서로 다른 예약을 본다.

### 준비는 되어 있다

- 예약마다 **`id`와 `updatedAt`** 이 이미 들어 있다. 여러 기기 데이터를 합칠 때 이게 없으면 통째로 갈아엎어야 한다
- 저장 담당(`store.js`)이 화면과 분리돼 있어 **그 파일 하나만 바꾸면** 저장 위치를 폰에서 서버로 옮길 수 있다

### 그때 치를 값

| | |
|---|---|
| 비용 | 무료 등급으로 2~3명은 커버 가능 |
| **개인정보** | 손님 이름·시술이 **클라우드로 나간다.** 지금은 폰 안에만 있어 없던 걱정 |
| 로그인 | 계정이 생긴다 |
| **관리 부담** | **"영원히 내가 관리해야 하는" 문제가 다시 생긴다** |

마지막이 가장 무겁다. 지금 구조의 최대 장점이 **만든 사람이 손을 떼도 앱이 안 죽는 것**인데, 서버가 생기면 사라진다.

**실제로 직원이 생기면 그때 다시 설계하는 게 맞다.**
