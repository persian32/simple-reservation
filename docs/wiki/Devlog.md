# 개발 기록

작업별 리뷰 → 병합 전 전체 리뷰 → 실사용 순으로 층층이 걸렀다. **각 층에서만 잡히는 문제가 따로 있었다.**

---

## 층 1 — 작업별 리뷰가 잡은 것

각 작업이 끝날 때마다 별도 리뷰어가 diff 를 검사했다. 여기서 잡힌 건 대부분 **계획서 자체의 결함**이었다.

**`npm test` 명령이 안 돌아갔다**
계획서에 `node --test test/` 라고 썼는데 Node 24는 `test/` 를 디렉터리가 아니라 *파일*로 해석해 실패한다. 경로를 빼면 자동 탐색한다.

**import 지시가 기존 코드를 깨뜨렸다**
"파일 맨 위 import 줄을 아래로 바꾼다"고 썼는데, 그대로 하면 앞 작업에서 넣은 `dates.js` import 가 사라져 홈 화면이 통째로 죽는다. 구현자가 발견해 '교체'가 아니라 '추가'로 처리했다.

---

## 층 2 — 전체 리뷰가 잡은 것

모든 작업이 끝난 뒤 브랜치 전체를 한 번에 봤다. **여기서 나온 5건은 전부 "조각으로는 정상인데 합치면 문제"** 였다.

**지난 날짜로 저장하면 조용히 사라졌다**
홈은 `date >= today` 만 그리는데 폼은 과거 날짜를 막지 않았다. 저장했는데 화면에 변화가 없으니 사용자는 "저장이 안 됐네" 하고 다시 넣는다 → **손님 이력에 같은 방문이 두 번 쌓인다.** 폼(작업 5)과 필터(작업 4)를 따로 보면 둘 다 정상이다.

**손님 이력에 도달할 길이 하나뿐이었다**
이력으로 가는 입구가 "홈에 뜬 이름 누르기"뿐인데, 홈은 다가올 예약만 보여준다. → **다가올 예약이 없는 손님의 이력은 열 수 없었다.** 그런데 이력을 보고 싶은 순간은 *손님에게 전화가 왔을 때*이고, 그때 그 손님에게는 예약이 아직 없다. **순서가 거꾸로였다.** → 손님 목록 화면을 추가했다.

**이름 오타로 이력이 갈라진다**
`byCustomer` 는 완전 일치 비교라 "화선언니"/"화선 언니" 한 번이면 이력이 조용히 둘로 쪼개진다. **되돌릴 방법이 없다.** → 자동완성 추가.

## 층 3 — 실제로 눌러봐야 나온 것

**이 층이 가장 값졌다.** 리뷰어 여섯 명이 통과시킨 코드에서 나왔다.

### 서비스워커 두 버그

**① 캐시가 새 파일과 옛 파일을 섞어 저장했다**

```
Uncaught SyntaxError: The requested module './services.js'
does not provide an export named 'createServices'
```

`cache.addAll()` 은 기본적으로 브라우저의 HTTP 캐시를 쓴다. 그래서 새 `home.js` 와 옛 `services.js` 가 한 캐시에 같이 들어갔고, 새 코드가 옛 파일에 없는 함수를 찾다가 **앱 전체가 죽었다.**

→ `new Request(f, { cache: 'reload' })` 로 서버에서 새로 받게 했다.

**② 등록 코드가 `home.js` 맨 아래에 있었다**

`home.js` 는 3번째 줄에서 죽는다. 그러니 맨 아래의 `serviceWorker.register()` 가 **아예 실행되지 않는다.**

> **한 번 깨진 기기는 새 버전을 영영 못 받는다.** 아무리 고쳐 올려도 안 고쳐진다. 사용자는 앱을 지우는 수밖에 없고, 그러면 예약 데이터도 같이 사라진다.

→ 등록을 `index.html` 인라인 스크립트로 옮겼다. **앱 코드가 죽어도 등록은 살아 있어야 자가복구가 된다.**

**왜 리뷰가 못 잡았나:** ①은 브라우저의 HTTP 캐시라는 *바깥 상태*가 끼어야 나타난다. ②는 앱이 정상일 때는 아무 문제가 없다. **깨졌을 때만** 드러난다.

### 시술 추가칸을 사용자가 못 찾았다

기능은 처음부터 동작했다. id·클래스·함수 호출 전부 맞았고 리뷰어 여럿이 통과시켰다. 그런데 **사용자가 못 찾았다.**

- 목록의 마지막 줄과 구분이 안 됐다 (구분선 하나 차이)
- "여기서 새로 추가한다"는 안내가 **한 글자도 없었다**
- 숫자 칸 옆에 **단위**가 없어 뭘 넣는 칸인지 몰랐다

→ 테두리 박스로 떼어내고, "새 시술 추가" 제목, "예: 세팅" placeholder, "분쯤 걸림" 단위를 넣었다. 겸사겸사 추가 버튼 높이가 **23px로 찌그러져 있던 것**도 발견했다.

### 애초에 위치가 틀렸다

사용자가 시술 추가를 찾으러 **세 번 연속 예약 폼으로 왔다.** 세 번 다 "거기 말고 설정으로 가세요"라고 답한 것이 잘못이었다.

**시술을 고르는 자리가 곧 "목록에 없네"를 발견하는 자리다.** 그 순간 사용자는 거기서 해결하고 싶어 한다. 설정으로 가라는 건 파일 구조를 아는 사람의 사고방식이지, 예약을 잡고 있는 미용실 사장님의 사고방식이 아니다.

→ 시술 드롭다운 맨 끝에 `+ 새 시술 추가…` 를 넣었다.

## 배운 것

### 코드를 짜기 전 단계는 싸고, 코드는 비싸다

처음 세운 가설(깜박한다, 알림이 필요하다)이 전부 틀렸다. 물어보지 않았다면 **아무도 안 쓸 앱을 몇 주 만들었을 것이다.**

### 같은 자리에서 두 번 헤매면 설계 문제다

사용자 문제가 아니다. 세 번은 확실하다. **"거기 있잖아요"를 반복하는 건 논쟁을 이기고 사용자를 잃는 것.**

한 문장이면 끝났다 — **"지금 어느 화면에서 찾고 계세요?"**

### 전제가 사라지면 결론도 다시 봐야 한다

"터치로 예약 시간 옮기기"를 뺀 근거는 **"종이가 원본이라 앱에서 고쳐봐야 다음 사진이 덮어씁니다"** 였다. 그런데 **사진 판독을 빼면서 그 전제가 사라졌는데도 결론만 남아 있었다.**

그 탓에 **주 4~5회 일어나는 일에 대응이 없는 앱**이 배포될 뻔했다.

> 큰 결정을 뒤집을 때는, **그 결정에 딸려 있던 작은 결정들을 목록으로 다시 훑어야 한다.** 사진 판독 제외는 *비용* 결정이었는데 거기에 *설계* 결정 셋이 딸려 있었고, 그중 하나만 재검토했다.

### 의존을 끊으면 검증 부담이 호출자 전수 확인으로 옮겨간다

`store.js` 가 시술 목록을 모르게 만든 덕분에 시술 관리 기능이 저장소를 **한 줄도 안 건드리고** 들어갔다. 대신 "화면이 정말 항상 소요시간을 넘기는가"를 `grep` 으로 호출처를 다 세어봐야 했다.

**계약을 바꿀 때마다 호출처를 전부 세는 습관이 여기서 나온다.**

### 리뷰 두 겹

작업별 리뷰는 "이 조각이 맞나", 전체 리뷰는 "합쳐놓으니 어떤가"를 본다. **층 2에서 나온 5건은 전부 후자에서만 보이는 것들이었다** — 각 조각은 다 정상이었다.

혼자 만들 때도 **다 만든 뒤 처음부터 한 번 통으로 읽는 시간**을 따로 두면 같은 효과가 난다.

### 그리고 결국, 사람이 눌러봐야 한다

층 3은 어떤 정적 검사로도 나오지 않았다. **"사람이 이걸 찾을 수 있나"는 코드를 읽어서 알 수 없다.**
