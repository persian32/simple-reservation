# 헤어살롱 예약 앱 — 설계 문서

작성일: 2026-07-28
작성: 정화선 + Claude (브레인스토밍 대화 기록 기반)

---

## 1. 배경

단골 헤어샵 사장님("언니")을 관찰한 데서 출발했다.

- 예약은 **본인 휴대폰으로만** 받는다. 가게 유선전화는 없다.
- 통화 중에는 폰을 귀에 대고 있어서 화면을 볼 수 없다. **빈 시간 확인은 벽에 걸린 월간 달력**으로 한다.
- 전화를 끊은 직후 달력에 볼펜으로 적는다.
- 하루 예약 5~10건. 혼자 받는다(직원 1명 있으나 예약은 받지 않음).

### 관찰과 확인의 차이

처음 가정했던 문제("퇴근 전 모바일 달력으로 옮기는 걸 깜박한다")는 **확인 결과 실제 문제가 아니었다.**

| 처음 가정 | 확인된 사실 |
|---|---|
| 예약을 깜박해서 곤란하다 | 깜박한 적이 거의 없다 |
| 옮겨 적는 게 불편하다 | 불편을 크게 느끼지 않는다 |
| 알림이 필요하다 | 놓친 적이 거의 없다 (늦잠 케이스만) |

**언니는 지금 불편하지 않다.** 이 앱은 사용자가 관찰 끝에 "선물로 주고 싶어서" 만드는 것이다. 이 사실이 설계 전체를 지배한다 — 불편하지 않은 사람은 앱이 조금만 귀찮아도 3일 만에 안 연다.

---

## 2. 목표

**성공 기준: 언니가 한 달 뒤에도 앱을 열고 있는가.**

기능 완성도나 코드 품질이 아니라 이것 하나다.

### 이 앱이 종이 달력보다 나은 단 하나

**손님 이력.** 이름을 누르면 이 손님이 언제 와서 뭘 했는지 나온다.

```
화선언니
   3/17 (화)          염색
   1/20 (화)          펌
  11/28 (금)          염색
  ────────────────────────
  총 8회 방문 · 평균 7주마다
```

언니는 단골이 많아 "이름만 적어도 시술이 기억난다"고 한다. 그 기억이 지금은 머릿속에만 있다. 지나간 달력은 버려지고, 작년 기록은 없다. **앱은 사진만 계속 찍으면 저절로 쌓인다.**

### 비목표 (의도적으로 안 만드는 것)

| 안 만드는 것 | 이유 |
|---|---|
| 손님이 직접 예약 넣기 | 사장이 전부 통제하는 시스템. 손님 상호작용 불필요 |
| 종이 달력 대체 | 통화 중엔 화면을 못 보므로 종이는 없앨 수 없다 |
| 직원 공유 / 서버 동기화 | 지금은 혼자. 몇 년 뒤 얘기이고 서버비가 발생한다 |
| 매출·통계 | 요청되지 않음 |
| 시술 여러 개 동시 선택 | 빈도 미확인. 터치 수를 늘려 입력 속도를 해친다 |
| 예약 변경 이력 저장 | 종이가 원본이므로 무의미 |
| 아침 알림 (1단계) | 아래 5-4 참고 |

## 3. 핵심 설계 원칙

### 원칙 1 — 종이가 원본이고 앱은 거울이다

언니는 지금 하던 대로 종이에 쓴다. 앱은 그것을 복사한다.
사진을 찍으면 그 기간의 예약을 갱신한다. 언니가 종이에서 시간을 고치거나 취소선을 그으면 다음 사진에 그대로 반영된다.

→ **"앱과 종이가 어긋나는" 문제가 구조적으로 발생하지 않는다.**
→ 앱에서 예약을 직접 편집할 이유가 거의 없어진다. 편집 기능은 "AI 오인식 수정"과 "급할 때 직접 추가" 용도로 축소된다.

### 원칙 2 — 언니가 새로 하는 일은 사진 한 장뿐이다

하루 한 번, 5초. **같은 일을 두 번 시키면 안 쓴다.** 이것이 예약마다 앱에 입력하는 방식을 버린 이유다.

### 원칙 3 — 사진 판독은 부가 기능이다. 없어도 앱은 온전히 동작한다

AI 판독만이 유일한 유료 요소다. 이 기능이 꺼져 있어도 예약 목록, 손님 이력, 직접 입력, 데이터 저장은 전부 정상 동작해야 한다.

### 원칙 4 — 데이터는 언니 폰 안에만 있다

서버 없음. 계정 없음. 로그인 없음.
→ 운영비 0원, 개인정보 유출 경로 없음, 개발자가 손을 떼도 앱이 죽지 않는다.

### 원칙 5 — 상태를 두 군데서 관리하지 않는다

AI 판독의 켜짐/꺼짐은 **AI 열쇠의 존재 여부**로만 결정한다. 별도의 On/Off 스위치를 두지 않는다.

## 4. 비용 구조 — "영원히 내야 하는 의무"를 없앤 설계

이 프로젝트의 가장 큰 제약은 **"언니는 돈을 내지 않는다"** 와 **"만든 사람도 영원히 매달 낼 수는 없다"** 가 동시에 성립해야 한다는 점이었다.

해법: **AI 열쇠를 코드에 박지 않고 앱 설정 화면에서 입력받는다.**

```
설정
  AI 열쇠 (선택)
  ┌──────────────────────────┐
  │                          │
  └──────────────────────────┘
  넣으면 달력 사진을 찍어 자동으로 읽을 수 있습니다.
  비워두면 직접 입력만 됩니다.
```

이 한 가지 결정이 세 문제를 동시에 푼다.

| 문제 | 해결 |
|---|---|
| 열쇠를 코드에 넣으면 도난 위험 → 서버 필요 | 열쇠가 사용자 본인 것이므로 숨길 필요 없음 → **서버 불필요** |
| 개발자가 영원히 비용 부담 | 열쇠를 언니에게 넘기면 손을 뗄 수 있음 |
| 개발자가 서비스를 해지하면 앱이 죽음 | 서버가 없으므로 죽을 것이 없음 |

### 비용표

| 항목 | 비용 |
|---|---|
| 웹앱 호스팅 (정적 파일) | **0원** — 무료 호스팅 |
| 데이터 저장 | **0원** — 폰 안 |
| 예약 목록 / 손님 이력 / 직접 입력 | **0원** |
| AI 사진 판독 | 사진 1장당 약 20원 (열쇠 주인 부담) |

사진 판독 사용 시: 하루 1장 기준 **월 약 630원** (Claude Sonnet 5, 2026년 8월 31일까지 할인가 기준. 이후 약 960원)

### 검토했으나 채택하지 않은 대안

| 대안 | 기각 이유 |
|---|---|
| 무료 등급 AI (Gemini 등) | 손님 이름·시술이 AI 학습에 사용됨. 언니가 모르는 채로 고객 정보가 나감 |
| 언니 폰에 AI 설치 (온디바이스) | 웹앱에서 접근 불가 → 네이티브 앱 필요. 모델 2~5GB 설치를 언니가 해야 함. 한글 손글씨 정확도가 클라우드보다 크게 떨어짐 |
| 개발자 서버(Railway)에 얹기 | 개인 프로젝트와 고객 데이터가 섞임. 매달 비용 발생. 해지 시 앱 정지 |

## 5. 화면 설계

화면은 넷. 하루 5~10건짜리 가게에 화면이 많아지면 길을 잃는다.

### 5-1. 홈 — 앱을 열면 바로 이것

```
┌────────────────────────────────┐
│  3월 2026            [📷 사진] │  ← 열쇠 있을 때만 보임
├────────────────────────────────┤
│  오늘  3/17 (화)               │
│                                │
│   10:20   화선언니      염색   │
│   14:00                 컷트   │
│   18:00   김미영        펌     │
│                                │
│  내일  3/18 (수)               │
│                                │
│   11:00                 파마   │
│                                │
│         [ + 직접 추가 ]        │
└────────────────────────────────┘
```

- 오늘 → 내일 → 이번 달 순으로 아래로 이어진다
- **이름이 없는 예약은 빈칸으로 둔다.** 언니가 종이에 안 썼으면 앱도 모르는 게 맞다
- 이름을 누르면 손님 이력 화면으로 이동
- 취소된 예약은 회색 + 취소선으로 남긴다 (삭제하지 않음 — 재방문 패턴 파악에 쓰인다)

### 5-2. 사진 확인 — 판독 직후 (AI 열쇠 있을 때만)

```
┌────────────────────────────────┐
│  사진에서 6건을 읽었어요        │
├────────────────────────────────┤
│  3/9 (월)                      │
│   10:00                 염색   │
│   14:00                 컷트   │
│                                │
│  3/11 (수)                     │
│   11:00                 파마   │
│   15:00                 매직   │
│   18:00                 클리닉 │
│                                │
│  3/17 (화)                     │
│  ▓10:20▓  ▓화선언니▓    염색   │
│   ↑ 확실하지 않아요. 확인해주세요│
├────────────────────────────────┤
│         [ 저장하기 ]           │
└────────────────────────────────┘
```

**핵심은 노란 표시다.** AI가 자신 없어 하는 항목만 색으로 띄운다. 6건을 다 검사하는 게 아니라 노란 것 한두 개만 보면 된다.

실제 테스트에서 "화선언니"를 "화선이나"로 오독했다. 이 화면이 없으면 그 오류가 그대로 저장된다.

### 5-3. 손님 이력 — 앱의 존재 이유

```
┌────────────────────────────────┐
│  ←  화선언니                   │
├────────────────────────────────┤
│   3/17 (화)          염색      │
│   1/20 (화)          펌        │
│  11/28 (금)          염색      │
│   9/30 (월)          염색      │
│  ────────────────────────      │
│  총 8회 방문                   │
│  평균 7주마다 오심              │
└────────────────────────────────┘
```

이름이 같은 예약을 모아 보여준다. 사진만 계속 찍으면 저절로 쌓인다.

### 5-4. 설정

AI 열쇠 입력칸 하나 + 데이터 내보내기 버튼.

**내보내기**: 누르면 예약 전체가 파일 하나로 떨어진다. 언니가 자기 카톡으로 보내두면 백업이 된다. 폰이 고장 나면 데이터가 날아가므로 이 버튼이 유일한 안전장치다.

### 색 사용 규칙

색은 딱 두 군데만 쓴다.

- **노랑** — AI 판독이 확실하지 않은 항목
- **회색 + 취소선** — 취소된 예약

시술별로 색을 다르게 하는 안은 기각했다. 하루 5~10건이 시간순으로 줄 서 있으면 색 없이도 한눈에 들어오고, 일곱 가지 색이 섞이면 오히려 시끄럽다. 색이 적을수록 그 색이 나타났을 때 눈에 띈다. 써보고 요청이 나오면 그때 넣는다.

### 알림에 대하여 (1단계 범위 밖)

언니는 "아침에 그날 예약 전체를 한 번" 받고 싶다고 했다. 하지만 **서버 없이 웹앱이 앱을 닫은 상태에서 알림을 보내는 것은 불가능하다** (웹 푸시는 푸시 서버가 필요하다).

원칙 4(서버 없음)를 지키기 위해 알림은 1단계 범위에서 제외한다. 임시 대체: 폰 기본 알람을 매일 아침에 맞춰두고 앱을 여는 습관.

언니가 놓친 유일한 실제 사례가 "늦잠"이었으므로 손실은 크지 않다고 판단한다.

## 6. 데이터 구조

### 예약 (reservation)

| 필드 | 설명 |
|---|---|
| `id` | 고유 번호 |
| `date` | 날짜 (2026-03-17) |
| `time` | 시작 시각 (10:20) |
| `customerName` | 손님 이름 (없을 수 있음 — 언니가 안 적는 경우가 많다) |
| `service` | 시술 (아래 목록 중 하나) |
| `durationMin` | 예상 소요 시간(분) |
| `status` | `active` \| `cancelled` |
| `source` | `photo` \| `manual` |
| `createdAt` / `updatedAt` | 생성·수정 시각 |

`id`와 `updatedAt`은 지금 쓰지 않는다. 몇 년 뒤 서버를 붙여 직원과 공유할 때 이 두 필드가 없으면 데이터를 갈아엎어야 하므로 미리 넣어둔다. 지금 비용은 0이다.

### 시술 목록과 기본 소요 시간

| 시술 | 기본 시간 | 출처 |
|---|---|---|
| 남자커트 | 30분 | **확인됨** |
| 펌 | 150분 | **확인됨** (120~180분 사이) |
| 여자커트 | 40분 | 임시값 — 언니 확인 필요 |
| 염색 | 90분 | 임시값 — 언니 확인 필요 |
| 매직 | 150분 | 임시값 — 언니 확인 필요 |
| 클리닉 | 40분 | 임시값 — 언니 확인 필요 |
| 기타 | 30분 | 임시값 |

임시값은 언니에게 확인하기 전까지의 자리채움이다. 어차피 앱에서 조절 가능하므로 틀려도 치명적이지 않지만, 기본값이 실제와 멀면 손을 대야 하는 횟수가 늘어 입력 속도를 해친다.

기본 시간은 자동으로 채워지고, **+/− 버튼으로 10분 단위 조절**이 가능하다. 손님의 머리숱·기장에 따라 같은 시술도 시간이 달라지며, 이는 사장만 아는 영역이기 때문이다.

> 유의: 언니는 종이 달력에 소요 시간을 적지 않는다. 머릿속에 있다. 따라서 앱에서 시간을 입력하는 것은 **언니 입장에서 지금 안 하던 일이 하나 느는 것**이다. 반드시 기본값이 자동으로 채워져 손을 안 대도 넘어가야 한다.

### 사진 판독 시 덮어쓰기 규칙

**사진은 사진이 만든 것만 지울 수 있다.**

새 사진을 판독하면 해당 기간의 `source: photo` 예약만 갈아엎고, `source: manual` 예약은 보존한다. 그래야 급할 때 손으로 넣은 예약이 사라지지 않는다.

중복(손으로도 넣고 종이에도 쓴 경우)은 확인 화면에서 "이미 있는 예약 같습니다"로 표시하고 **사람이 판단**한다. 자동 병합하지 않는다 — "10시 염색"과 "10시 염색"이 같은 손님인지 다른 두 손님인지 기계는 알 수 없고, 잘못 지우는 손해가 훨씬 크다.

### 저장 방식

브라우저 `localStorage`에 JSON 한 덩어리로 저장한다.

예약 1건 약 100바이트 × 연 3,000건 = 연 300KB. 5년 써도 1.5MB로 localStorage 한도(약 5MB) 안에 들어온다.

> `ponytail: localStorage 전체를 매번 읽고 쓴다. 수천 건까지는 체감 지연이 없다. 느려지면 IndexedDB로 옮긴다.`

## 7. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 형태 | 웹앱 (PWA) | 아이폰·갤럭시 한 벌로 커버. 설치·심사·개발자 계정 불필요. **고치면 즉시 반영** — 첫 앱에는 버그가 반드시 나오고, 매번 재설치를 부탁할 수 없다 |
| 프론트엔드 | 순수 HTML/CSS/JS | glean에서 이미 해본 방식. 프레임워크 없이 구조를 전부 이해하려는 학습 목적 |
| 저장 | localStorage | 서버 없음 |
| AI 판독 | Claude Sonnet 5, 브라우저에서 직접 호출 | 손글씨 정확도. 2576px 고해상도 입력 지원(Haiku는 1568px로 축소되어 손글씨가 뭉개진다) |
| 배포 | 무료 정적 호스팅 | 파일만 올리면 끝. 운영비 0원 |
| 설치 | 홈 화면에 추가 | 갤럭시는 앱 서랍에도 들어가고 주소창 없이 전체화면으로 뜬다 |

### glean에서 가져오는 것

`~/Desktop/Developer/glean`에서 이미 완주한 경험이 그대로 적용된다. 코드를 복사하는 것이 아니라 **패턴을 재사용**한다.

- Claude API에 이미지를 base64로 보내고 JSON을 받는 흐름 (`lib/ai.js`, 45줄)
- 정답 목록으로 결과를 교정하는 장치 — glean의 `CATEGORIES.includes(...) ? ... : '기타'` 를 시술 7종에 그대로 적용
- 이미지 압축, PWA 설치, `node --test` 기반 TDD

**glean과는 저장소·배포를 완전히 분리한다.** glean은 개인 기록이고 이 앱은 가게 손님 정보다.

## 8. 단계별 계획

### 0단계 — 검증 (코드 없음, 반나절)

**언니의 실제 달력 사진**을 받아 AI에게 넣어본다.

이 앱 전체가 "AI가 언니 손글씨를 읽을 수 있다"는 가정 위에 있다. 아직 검증되지 않았다 — 지금까지 테스트한 사진은 사용자가 흉내 낸 글씨였다.

| 결과 | 다음 |
|---|---|
| 잘 읽힌다 | 2단계로 |
| 반쯤 읽힌다 | 찍는 방법을 바꾸거나 언니에게 최소한의 부탁 하나를 얹는다 |
| 거의 못 읽는다 | 사진 판독을 영구히 접는다. 1단계 앱만 완성 |

### 1단계 — 손 입력 앱 (비용 0원)

홈 화면, 직접 추가, 손님 이력, 설정, 내보내기.
이 단계만으로 **완결된 앱**이다. AI 없이도 온전히 동작한다.

### 2단계 — 사진 판독 (0단계가 성공했을 때만)

설정에 AI 열쇠 칸을 추가하고, 열쇠가 있으면 카메라 버튼과 확인 화면이 나타난다.
1단계 코드를 뜯어고치는 게 아니라 **버튼 하나와 화면 하나를 얹는 것**이 된다.

### 3단계 — 실사용 확인

언니 폰에 설치하고 2주 지켜본다. **여전히 열고 있는가**가 유일한 질문이다.

### 순서를 지켜야 하는 이유

화면을 예쁘게 다 만들어놓고 마지막에 판독을 붙였다가 "언니 글씨는 못 읽네"가 나오면 전부 헛일이 된다. **제일 위험한 가정을 제일 먼저, 제일 싸게 검증한다.**

## 9. 확인되지 않은 것 · 위험

| 위험 | 수준 | 대응 |
|---|---|---|
| **언니 실제 손글씨를 AI가 못 읽는다** | 높음 | 0단계에서 먼저 검증 |
| **언니가 사진 찍는 습관을 안 들인다** | 높음 | 3단계에서 확인. 이것이 실패하면 앱 자체가 실패 |
| 칸 밖으로 빼서 쓴 글씨(사선 표시)의 날짜를 AI가 헷갈린다 | 중간 | 확인 화면에서 사람이 잡는다 |
| 이름 오인식 | 중간 | 노란 표시 + 사람 확인. 시술명과 달리 대조할 목록이 없어 근본 해결은 불가 |
| 폰 고장 시 데이터 유실 | 중간 | 내보내기 버튼. 언니에게 주기적 백업을 부탁 |
| 무료 호스팅 정책 변경 | 낮음 | 정적 파일이라 다른 곳으로 옮기는 데 몇 분 |

## 10. 언니에게 물어보거나 관찰할 것

설계에 반영하지 못하고 남긴 항목들이다.

**물어볼 것**

1. 한 손님이 두 가지 이상을 같이 하는 경우(커트+염색)가 자주 있나? → 자주면 시술 다중 선택 필요
2. 여자커트·클리닉의 실제 소요 시간은? (남자커트 30분, 펌 120~180분만 확인됨)
3. 예약을 바꾸면 달력에 어떻게 고쳐 쓰나? (지우나, 화살표를 긋나)

**눈으로 볼 것** — 사람은 자기 습관을 정확히 기억하지 못한다.

1. 실제 예약이 적힌 벽 달력 사진 (0단계 검증에 필수)
2. 전화를 끊은 뒤 달력에 적기까지 걸리는 시간 — 앱이 이겨야 할 기준

## 부록 — 기각된 초기 아이디어와 그 이유

브레인스토밍 과정에서 방향이 여러 번 바뀌었다. 나중에 같은 길을 다시 걷지 않도록 남긴다.

| 아이디어 | 기각 이유 |
|---|---|
| 예약마다 앱에 직접 입력 | 종이에도 쓰고 앱에도 쓰면 같은 일을 두 번 하는 것. 언니가 안 한다 |
| 앱으로 종이 달력을 대체 | 통화 중엔 폰 화면을 못 본다. 종이는 통화 중 조회용으로 필수 |
| 앱에서 터치로 예약 시간 옮기기 | 종이가 원본이면 앱에서 옮겨도 다음 사진이 덮어쓴다. 언니는 어차피 종이에서 고친다 |
| 아침 알림을 핵심 기능으로 | 언니가 예약을 놓친 적이 거의 없다. 아쉬워하지 않는 기능이었다 |
| 시술별로 색 구분 | 하루 5~10건이면 색 없이도 한눈에 들어온다. 색이 많으면 오히려 시끄럽다 |
| 음성 입력 전용 기능 | 키보드 마이크 버튼이 이미 음성 입력이다. 개발 0줄. 통화 중엔 마이크를 못 쓰고 미용실은 시끄럽다 |
| 서버(Railway)에 데이터 저장 | 열쇠를 사용자가 입력하게 하면서 서버가 통째로 불필요해졌다 |
| On/Off 스위치 + 열쇠 입력칸 | 열쇠 유무가 이미 스위치다. 상태를 두 군데서 관리하면 버그가 난다 |
